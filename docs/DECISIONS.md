# Decisions

- Agency is the tenant; v1 allows one connected WhatsApp business sender per agency to keep routing unambiguous.
- Composite foreign keys include agency_id to prevent cross-tenant relationships; outbound messages also bind the conversation and message together.
- Applied migrations are immutable and checksum-verified to detect drift; migration runs are transactional and serialized.
- Task 2.2 uses ENABLE and FORCE RLS on all nine application tables so table ownership alone cannot bypass policies.
- Runtime manzil_app must be a non-owner with no superuser, BYPASSRLS, or elevated role memberships; migration administration stays separate.
- Missing tenant context returns zero rows by design; trusted routing/discovery must supply context explicitly.
- Tenant context is UUID-validated and transaction-local; arbitrary customer input is not tenant authority.
- Reject nested/open transactions and session-level tenant context so connection reuse cannot silently inherit another tenant.
- Tests connect directly as the restricted login and CI requires PostgreSQL so bypass-role tests or skipped checks cannot masquerade as isolation proof.
- Reject unsafe existing role capabilities, memberships, ownership, and policies rather than silently widening runtime access.
- Keep estimated usage measurements null when unknown; do not invent zero costs or usage.
- updated_at is maintained by application code; schema v1 has no automatic timestamp trigger.
- Provider choices from handoff are Gemini for text/audio fallback and ElevenLabs Scribe for primary transcription; keys and current provider behavior remain unverified locally.
- Webhook callback path is /webhook. Signature is verified over raw bytes before parsing; missing app secret fails closed with 503; authentic but unusable payloads get 200 (retries cannot fix them). The verify token is redacted from access logs.
- Webhook routing (Task 2.4): demo uses an env map WEBHOOK_SENDER_AGENCIES behind a SenderResolver protocol, resolved before the tenant transaction and re-verified inside it against agency.meta_phone_number_id and is_active. No DB resolver, no extra RLS policy, no BYPASSRLS. Unknown/inactive senders are dropped with 200; misrouting or persistence failures return 503.
- Event keys: wa:msg:{wamid} and wa:status:{wamid}:{status}; jobs process_message / reconcile_status with matching dedupe keys. Event + job are written by one INSERT ... ON CONFLICT DO NOTHING statement per event.
- Worker (Task 3.1): tenant discovery reuses the trusted WEBHOOK_SENDER_AGENCIES map; every claim runs in tenant_transaction, so no RLS exception. Agencies are polled round-robin.
- Per-conversation serialisation: job.conversation_key (migration 003; contact wa_id for messages, NULL for statuses) + a session-level two-key advisory lock held by the claiming connection until the final status commits. A dead worker's lock drops with its connection; the lease reaper requeues a job only when its lock is free.
- Retries: back to pending with backoff 5 s x 2^(n-1), cap 300 s, +/-20% jitter; dead after max_attempts or PermanentJobError. last_error_code stores the exception class or explicit code, never the message. The 'failed' status stays unused.
- Only job types with a registered handler are claimed; others stay pending rather than dead-lettering. Handlers must be idempotent (lease expiry re-runs them).
- Next migration numbers: 003 is the job conversation key; 004 (Task 3.2) is the outbound delivery status; Taha's 3.3/3.4 migrations start at 005.
- Outbound (Task 3.2): outbound_message.status is the send pipeline (pending -> sending -> sent / failed / unknown / cancelled); delivery_status follows statuses webhooks and only moves forward (sent < delivered < failed < read; failed is terminal, a read message stays read).
- Sends are at most once: dedupe key = job-derived key + sequence (turns use turn:{turn_id}:{seq}; the Task 3.2 echo used echo:{wamid}:{seq}). A row found still 'sending' on retry, a read timeout, or a dropped connection becomes 'unknown' and is never resent (the Cloud API has no idempotency key). Connect failures, 429, 5xx and Meta throttling codes are retried.
- Send-time control gate (R-28) runs in the transaction that marks the row 'sending': AI-generated messages are cancelled unless conversation.mode = 'ai'; holding replies pass ai_generated=False. Session messages outside the 24 h window are recorded failed/outside_window.
- A status webhook that arrives before its send is recorded is retried; on the last attempt an unmatched status (e.g. a dashboard-sent template) succeeds as a logged no-op.
- The echo bot (app/echo.py) was temporary; Task 5.1 replaced its replies with the C3 orchestrator and kept only the '#demo <type>' samples, for staff / admin turns. '#demo <type>' sends fictional samples; '#demo image' uses a 10-minute presigned link to demo/echo-test.jpg in the private bucket.
- The demo WhatsApp token comes from META_ACCESS_TOKEN; without it the worker registers only reconcile_status, so message jobs wait pending instead of failing.
- Inventory (Task 3.3, migration 005; details in docs/INVENTORY_SCHEMA.md). Written before the RFC data model (D11) and Red-Team documents were available; the decisions below were recorded assumptions. 005 is applied on RDS; its gaps against D11 / R17 (ZONE level, location codes, on_hold / archived, D11 types and investment / possession fields, nominal size bucket, last_confirmed_at, and others) are listed in docs/SPEC_ALIGNMENT.md and need a new forward migration. Owner decision 2026-10-08: 005 is not modified, and the D11 inventory changes are a separate follow-up task and PR before the Task 4.3 seed, not part of the Task 3.4 branch.
- Gazetteer tables (location, location_alias, location_neighbor) are shared, have no agency_id and no RLS; manzil_app gets SELECT only and PUBLIC nothing. FORCE RLS without a tenant column would add nothing and would block the admin seed load (4.3).
- Location hierarchy is strict city -> area -> sub_area, enforced by a CHECK plus a composite FK on (parent_id, parent_level); cycles are impossible. Names are unique per parent (case-insensitive, NULLS NOT DISTINCT). Aliases may map to several locations (ambiguity is resolved by 7.1, not prevented); only exact duplicates per (location, alias, context) are rejected. Area-scoped short forms ("phase 8" in DHA) are context aliases.
- location_neighbor is symmetric, stored once per pair with location_a_id < location_b_id.
- pg_trgm is created by the migration only when absent; the index uses the schema the extension actually lives in. A migration role that cannot create it fails clearly; no broad privilege is granted for tests (the non-superuser migration test pre-installs it, as a DBA would).
- Lowercase status values (active, reserved, sold, rented, withdrawn); withdrawn removes a listing without deleting it. Staff roles stay admin / agent / broker (Demo Scope "STAFF" = agent).
- Unknown property facts are NULL. Incomplete inventory lives in listing_draft; the minimum-to-save set (Demo Scope S4: purpose, type, location, size, price, + bedrooms for house / apartment / portion) is a CHECK on status = 'active' only.
- Rent price_pkr is per month; sale price_pkr is the total. area_sqft is a STORED generated column with sq yd = 9, marla = 225, kanal = 4500 sq ft (plan 6.2); the stated value and unit are kept. PostgreSQL 18 defaults generated columns to VIRTUAL, which cannot be indexed, so STORED is explicit.
- Cover media is a composite FK (agency_id, id, cover_media_id) -> property_media (agency_id, property_id, id) ON DELETE SET NULL (cover_media_id).
- Runtime cannot DELETE project or property (listings leave by status). property_event is append-only for the runtime (SELECT, INSERT); an undo may only reference an event of the same property.
- One open update draft per staff member and target property (partial unique index); several staff may draft the same property and create drafts are unlimited. Concurrent edits are settled at save time by an atomic UPDATE ... WHERE version = base_property_version (future 9.2 handler); the Demo Scope wording "one open draft per listing" was relaxed to this by the owner on 2026-10-08.
- staff_session is temporary WhatsApp workflow context (one row per staff member), not authentication; it stores no tokens.
- v_public_listing is security_invoker + security_barrier, an explicit column allowlist and status = 'active' only. It is the customer-safe interface but not a complete privilege boundary while manzil_app can read property.
- .gitattributes forces `*.sql text eol=lf`: the runner checksums raw migration bytes, so checkout line endings must never change them. Checksum validation itself stays strict.
- is_demo is not filtered by the view: demo isolation comes from tenancy (demo rows belong only to the demo agency). Production agencies must have no is_demo rows; database enforcement needs an agency-level flag later.
- Conversation state (Task 3.4, migration 006; details in docs/STATE_SCHEMA.md). First drafted from the execution plan and the 3.1/3.2 handoff; after the owner shared the reference set on 2026-10-08 (RFC v1.0, Red-Team, Demo Scope, D11, R17/R18, R6 and others; kept outside the repo), 006 was aligned to R17 section 5, R6 / D4 and Red-Team R-28...R-31. Remaining deviations are listed in docs/SPEC_ALIGNMENT.md.
- conversation.control_state (ai_active, handoff_pending, human_owned, closed) is added as a foundation only. mode, ai_muted_until and the mode-based send gate in app/outbound.py are kept unchanged for backward compatibility (owner decision 2026-10-08; departs from Red-Team R-28, which gates on control_state). Control-state integration (gate, orchestrator control gate, handoff transitions) is pending and belongs to the orchestration / handoff tasks (5.1, 11.1, 11.2).
- Backfill: ai -> ai_active; human and paused -> human_owned. paused must never map to an AI state; handoff_pending needs an open handoff and closed could be silently reopened into AI, so neither is used. mode keeps 'paused', so no information is lost. ai_muted_until is not mapped (temporary, orthogonal, unused by code).
- The backfill lifts FORCE RLS on conversation inside the migration transaction (the owner has no policy, so a plain UPDATE would silently change nothing), asserts no silenced row stayed ai_active, and restores FORCE. ACCESS EXCLUSIVE keeps other sessions out until commit. Tested as a non-superuser owner, as on RDS.
- conversation_control_state_gate_check: control_state = 'ai_active' OR mode <> 'ai'. A silenced control state can never look AI-enabled to the mode gate; mode alone may still silence an ai_active row (existing behaviour). When the gate moves to control_state it should cancel if any of mode, control_state or ai_muted_until says silent.
- service_window_expires_at is not stored (owner decision 2026-10-08; a deliberate departure from R17 section 5 and RFC section 8, which list it). The 24 h customer-service window stays derived from last_customer_message_at (app/outbound.py), so it cannot go stale. A later task that needs a stored value must add it together with reliable update logic and tests. preferred_language and last_modality are nullable (unknown until the turn engine writes them).
- message.modality is a STORED generated column from message_type (text -> text, audio -> voice, else NULL), so rows written by the unchanged ingestion are correct; a 'text' default would mislabel voice notes. transcript / stt_meta are allowed only on inbound audio. New columns are not partially backfilled.
- Lead numbers: agency.next_lead_number plus next_lead_number() (SECURITY INVOKER, runs under RLS, EXECUTE for manzil_app only) allocate per agency in the inserting transaction; the agency row lock serialises allocation and a rollback returns the number. UNIQUE (agency_id, lead_number) is the backstop; MAX + 1 is never used. code is generated as L-NN (at least two digits, never truncated).
- One open lead, one open handoff (pending or accepted) and one open clarification per conversation are partial unique indexes. A lead may cover several confirmed properties (lead_property; "[Dono]", R-31); viewed properties come from shown_item. Broker [Called] and the outcome buttons (visit_booked / not_interested / deal; R6, RFC 7) are recorded on handoff; reassignment history (R-32) is a production item. focus is customer-conversation focus, separate from staff_session.focus_property_id.
- State histories (requirement_patch_log, search_run, shown_item) are append-only for the runtime; no new table grants DELETE. A shown card's WAMID is message.provider_message_id via card_message_id (not stored twice). media_sent keeps its row when the photo is deleted (ON DELETE SET NULL (property_media_id)).
- requirement_state.slots is restricted by CHECK to the 15 R17 slots, each an object with source text / voice / inferred / default. Patch ops are R17 RequirementPatch items {slot, op, raw_span}: op in set / add / remove / clear / relative and slot one of the 15 names (the 90-day reset is logged as clear ops). Clarification slots are location / purpose / target (R17 5) with an unanswered_turns counter (R17 edge 11). New slot names or ops need a migration.
- Treated as sensitive: transcripts, stt_meta, requirement slots and patch history, lead and handoff rows, and message references. Tenant-isolated, never logged, not deletable by the runtime.

Accepted, then a 'failed' status webhook before any 'delivered': reconcile_status queues one carousel_fallback job (dedupe key carousel-fallback:{outbound id}, conversation key = recipient), which sends through app.outbound under carousel-fallback:{outbound id}:{n}. An 'unknown' (ambiguous) carousel is never resent or fallen back (at most once); it has no WAMID, so no status can match it.

- Task 6.1 AI turn engine (owner decisions 2026-10-12; details in docs/AI_TURN_ENGINE.md). The demo LLM is Gemini behind a C6 adapter (app/llm.py: httpx, stateless generateContent; no SDK, no explicit cachedContents, no Interactions API), departing from RFC 9 / R16 D8 (Claude Opus 5.5 / Sonnet 5.5) for the demo only; moving back is a new adapter plus config. AI_PROVIDER=stub stays the default; AI_PROVIDER=gemini needs GEMINI_API_KEY, LLM_PRIMARY_MODEL and LLM_FAILOVER_MODEL and migrations 013 + 014 (checked before any job is claimed), or the worker exits with code 78 and a sanitised log (never a silent fallback; Compose restarts it under restart: unless-stopped). Model IDs have no defaults; the owner's pinned choice (2026-10-11) is gemini-3.5-flash-lite primary, gemini-3.6-flash failover (corrected 2026-10-12 from a 3.8-flash / 3.5-flash-lite proposal), still to be checked for account availability and free-tier limits before activation.
- Task 6.1 budget: 8 s per provider call, 15 s per turn, a call needs >= 1 s left, <= 3 iterations. After the TCP connect the deadline is enforced by a watchdog that shuts down its own dup() of the connection's socket (covers TLS, upload and reads; no keep-alive; nothing runs on after the call); DNS and the TCP connect are outside it, and database statements are bounded only by statement_timeout, so neither limit is a hard end-to-end guarantee. Failover only on the turn's first call (timeout, transport, 404 / 408 / 429 / 5xx) with the identical request; once a model has answered the turn stays on it, and a later failure ends the turn (thought signatures are not replayed to another model; tool actions are never replayed). No 30 s retry job in 6.1 (plan 13.1).
- Task 6.1 follow-up (owner 2026-10-12): Red-Team R-17 interim + continuation. When the 15 s turn budget runs out before an answer (no 1 s left for an attempt, or an iteration timed out), the customer gets "Ek minute, check kar raha hoon." once (turn:{id}:interim, at most once per turn, send-time gate) and the turn gets one 15 s continuation that retries the iteration (same model once one has answered); a second exhaustion ends with the failure template. Usage keys of continuation attempts end in ':c'. Thinking level: generationConfig.thinkingConfig.thinkingLevel = low by default (LLM_THINKING_LEVEL; 'off' omits it).
- Task 6.1 follow-up: no customer turn fails silently (RFC 13). A turn closed as 'failed' gets the failure template once (turn:{id}:failed) through the send-time gate, unless part of its reply was sent; one notice per job, before newer messages are answered. A process_message job that dies of a crash on its last attempt makes the lease reaper queue a turn_failed_notice job (same conversation key) that closes the turn (unless another job will resume it) and sends the notice.
- Task 6.1 replies: approved Roman Urdu templates plus notices from trusted tool results only; model prose is never sent (R-21). Refused (blockReason, SAFETY / PROHIBITED_CONTENT / BLOCKLIST / SPII / RECITATION) -> refusal template, no failover; malformed / truncated / other -> failure template; tools run only from STOP responses. Brokers and turns without text make no provider call. turn_engine.ground_reply is the seam for the 9.1 renderer + validator (listing-code check as defence in depth only).
- Task 6.1 tools: route from the allowlist only; customer, staff (admin / agent) and broker (none) registries; execution re-checks route and arguments (strict local schema); commit_change is never an LLM tool. 6.1 bodies are stubs that do and claim nothing; update_requirements checks raw spans against the turn text (R-22) without storing anything.
- Task 6.1 metering: one usage_event per provider attempt (primary and failover) in its own transaction after the call, request_key turn:{turn}:job:{job}:{job attempt}:{iteration}:{primary|failover}, plain INSERT. A usage INSERT error of SQLSTATE class 22 / 23 / 42 is permanent (PermanentJobError: no retry, no further provider call); other database errors use the job's bounded retries. A turn whose job will not retry is closed as 'failed' (migration 014), so later messages start a new turn; because a crash runs no cleanup, conversation_turn.attempts is counted at assembly and an open turn with 3 attempts is closed as 'failed' instead of resumed; a job whose last attempt fails an older turn still answers its own messages; a failed turn's pending trigger job is dead-lettered (turn_failed). The worker checks migration 014 at start with any AI_PROVIDER (and 013 with gemini). outcome = provider-call success, not task success; migration 013 adds cached_input_tokens, thinking_tokens and a sanitised outcome_detail. Tokens NULL when not reported; estimated_cost NULL until a free-tier policy for the key is verified.
- Task 6.1 replay: the reply plan is fixed in conversation_turn.reply_plan via cards.fixed_plan (no transaction or lock across provider calls). A stored plan is resent without a provider call; a crash before it is stored calls the provider again. Provider execution is at least once per turn attempt, not exactly once.
- Task 6.2 normalisers (owner decisions 2026-10-12; details in docs/NORMALISATION.md): app/normalise.py is pure deterministic code (no DB, no LLM, no dependency). A bare amount and "budget X" mean around +/-10 % (bench gold and BENCHMARK.md), departing from Data Model 4.3, which lists "budget X" with the max words; a max word still wins ("budget aath crore tak" = max). The stated amount is kept apart from min / max; the x 1.05 / x 0.9 search tolerances belong to 8.1.
- Task 6.2 rent / sale inference: Data Model 4.4's commercial rule is cut off in the PDF; owner decision: commercial <= 25 lakh rent, >= 1 crore sale, in between ask (residential unchanged: <= 15 lakh rent, >= 50 lakh sale). Inferred purpose is always source 'inferred', confirmed false (echo before the first search). Explicit wording wins, rent before sale; "lena hai" counts as sale even without an amount (bench CT-07 / CV-07), and a monthly amount marker (per month / mahana) counts as rent.
- Task 6.2 ambiguity: nothing is guessed. A missing unit for a house / plot / portion above 2,000, a missing unit with an unknown type, two amounts in one budget span and an amount between the rent and sale thresholds return status 'ambiguous'. Number words count as money or size only next to a multiplier or unit (so "do you" and "saath" = with are ignored).
